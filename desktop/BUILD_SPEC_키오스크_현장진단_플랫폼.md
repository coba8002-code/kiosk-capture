## 1. 핵심 설계 결정 — 판정기가 아니라 분류기

“AI가 접근성을 판정한다”는 명제는 성립하지 않는다. 별표5 항목의 상당수가
물리 치수와 물리력을 근거로 삼는다 — 버튼 표면적 144mm², 조작력 22.2N,
스피커 65dBA, 작동부 높이 400~1,220mm, 배출물 돌출 20mm.

그래서 이 시스템은 **판정 가능한 것과 불가능한 것을 갈라내고, 불가능한 쪽을
정확한 담당자에게 넘기는 분류기**로 설계한다.

| 트랙 | 항목 수 | 판정 주체 | 입력 |
|---|---:|---|---|
| **A · AI 자동** | 29 | AI 1차 → 검토자 확정 | 촬영물 |
| **B · 점주 셀프 체크** | 4 | 점주 현장 확인 | 예/아니오 문항 |
| **C · 전문 실측** | 7 | 계측 장비 | 줄자·힘게이지·소음계·조도계 |
| **D · 사용자 검증** | — | 장애인·고령자 12명 | **이 시스템의 범위 밖** |

그리고 A 트랙 29항목 안에서도 AI의 사정거리가 다르다.

| `ai_verdict_scope` | 항목 수 | 의미 |
|---|---:|---|
| `both` | 23 | 적합·부적합 양방향 제시 가능 |
| `fail_only` | 13 | **위반은 잡지만 적합을 증명하지는 못한다** |
| `none` | 4 | 맥락 자료만 제공 |

> AI가 ‘적합’까지 말할 수 있는 항목은 40개 중 23개(57%)뿐이다.
> 이 숫자를 숨기지 않고 리포트에 인쇄하는 것이 제품의 정직성이다.

## 2. 기술 스택

- **언어**: Python 3.11+ (촬영물 분석이 주 업무 — OpenCV·numpy 생태계)
- **룰 DB**: YAML (`rules/annex5.yaml`) — Git 버전 관리, 스프레드시트는 export 전용
- **L1 계측**: OpenCV + numpy. LLM 미사용
- **L2 판정**: 멀티모달 LLM. 프로바이더 추상화로 교체 가능
- **수집 앱**: PWA (모바일 웹). 스토어 심사·설치 장벽 없음
- **검토자 콘솔 / 리포트**: 웹. 리포트는 마크다운 → PDF
- **저장소**: 오브젝트 스토리지(촬영물) + PostgreSQL(판정 레코드)

> 자체 모델을 학습시키지 않는다. 3,600만 원 예산에서 성립하는 유일한 선택이며,
> 절약한 비용은 **룰 DB의 정확도와 촬영 프로토콜의 완성도**에 넣는다.
> 모델은 교체할 수 있지만 룰 DB는 이 사업이 남기는 유일한 자산이다.

## 4. 룰 DB 스키마 (`rules/annex5.yaml`)

항목 하나의 레코드:

```yaml
- id: "3.i"
  scope: 기본                  # 기본 | 물건 투입 | 스캐너 | 지문 인식 | 배출물 …
  applies_to: [중대형, 소형]    # 화면 대각선 28cm 기준
  criterion: >-                # 별표5 원문 (행정규칙 = 공공저작물, 인용 가능)
    모든 화면에 대해 필수적인 문자와 배경 간 4.5:1 이상의 명도 대비를 …
  verdict:
    base: 적합/부적합
    grade: null                # 우수/보통은 8개 항목만
  track: A_AI                  # A_AI | B_OWNER | C_MEASURE | D_USER
  ai_role: measure             # measure | judge | screen | none
  ai_verdict_scope: both       # both | fail_only | none  ← 정직성의 핵심
  final_by: REVIEWER           # REVIEWER | MEASURE | OWNER
  evidence: [S1]               # 필요한 촬영 세트
  marker_required: false
  params: { contrast_min: 4.5, formula: "WCAG relative luminance …" }
  logic_ref: "calc/contrast.py"
  ks_ref: ["KS X 9211:2025 §5.2.5"]     # 절 번호만. 본문 인용 금지(§10)
  remedy: { type: SW, difficulty: 낮음, cost_band: 1 }
  exemptible_by: [무인민원발급기_표준규격]
```

### 4.1 필드가 존재하는 이유

| 필드 | 없으면 무슨 일이 생기는가 |
|---|---|
| `criterion` + `id` | 리포트가 **법적 결론**을 낼 수 없다. 판정은 별표5 40항목 위에 찍힌다 |
| `track` | 미판정이 ‘실패’로 보인다. 트랙이 있어야 ‘다음 담당’이 나온다 |
| `ai_verdict_scope` | AI가 확정할 수 없는 항목에 ‘적합’을 찍는다 → 과태료 리스크 전가 |
| `logic_ref` | 같은 기기를 두 번 진단했을 때 결과가 달라진다 |
| `marker_required` | 마커 없이 픽셀을 mm 인 척 환산한다 |
| `remedy` | 리포트가 성적표에서 멈춘다 |

### 4.2 검증 게이트

`tools/validate_rules.py` 가 CI에서 다음을 강제한다.

- 필수 필드 존재 · 열거형 값 유효성
- 트랙과 사정거리의 정합성 (`track=A_AI` 인데 `scope=none` 금지 등)
- `track=B_OWNER` 는 `owner_question` 필수, `track=C_MEASURE` 는 `instrument` 필수
- `ai_role=measure` 는 `logic_ref` 필수
- 면제 경로가 실재 항목을 가리키는지 (양방향)
- 촬영 프로토콜과의 교차 검증 — `evidence` ↔ `feeds` 가 서로 맞는지
- `meta.total_items` / `graded_items` 가 실제와 일치하는지

```bash
python tools/validate_rules.py --coverage
```

> ⚠ YAML 1.1 함정 — 영역 번호 키를 `no:` 로 쓰면 boolean `False` 로 파싱된다.
> 이 스키마는 `area:` 를 쓴다. 새 키를 추가할 때 `no/yes/on/off` 를 피할 것.

## 5. 판정 모델 (`engine/verdict.py`) — 시스템의 심장

이 모듈의 존재 이유는 하나다. **AI가 자기 사정거리를 넘는 결론을 내지 못하게 막는 것.**

```
Verdict = 적합 | 부적합 | 위반 의심 | 미판정 | 해당 없음 | 면제
```

### 5.1 불변 규칙

1. **AI는 ‘부적합’을 확정하지 않는다.** AI의 FAIL 은 항상 `위반 의심`으로 강등되고,
   검토자 승인(`confirm`)을 거쳐야 `부적합`이 된다.
2. **`fail_only` 항목의 AI PASS 는 무조건 `미판정`으로 강등된다.**
   강등 사유(`NEEDS_MEASURE` / `NEEDS_OWNER`)는 `track` 이 아니라 **`final_by`** 가 정한다.
   (1.b 처럼 `track=A_AI` 이면서 적합 확정은 실측이 하는 항목이 있다.)
3. **근거 4종이 없는 판정은 버려진다** — 근거 이미지 크롭 · 측정값 · 항목 ID · 확신도.
4. **확신도가 `confidence_floor`(기본 0.85) 미만이면 검토자 큐로 간다.**
5. **검토자가 반려해도 ‘적합’이 되지 않는다.** 미판정으로 되돌아갈 뿐이다.
6. 실측·점주 판정(`record_external`)은 사정거리 제한을 받지 않는다.

모든 AI 판정은 `apply_ai_scope()` 를 통과해야 한다. `Assessment` 를 직접 생성하는
코드 경로가 생기면 이 규칙이 전부 무력화되므로, 코드 리뷰에서 차단한다.

## 6. 진단 엔진 — 3계층

### L1 · 결정론적 계측 (`engine/calc/`) — 코드가 계산한다

같은 입력이면 같은 값. 리포트에 수식과 측정값이 그대로 실린다. **법적 방어력은 여기서 나온다.**

| 모듈 | 항목 | 방법 |
|---|---|---|
| `contrast.py` | 3.i · 3.j | WCAG 상대 휘도. 사진 색 산포로 확신도 조정 |
| `scale.py` | 마커 환산 | 4점 호모그래피(DLT) → px/mm. 왜곡·해상도 게이트 |
| `geometry.py` | 1.b · 1.c · 1.i · 9.a · 9.b | mm 평면 위의 경계상자·간격·높이 |
| `text_height.py` | 3.g | OCR 박스 × 자종별 보정 계수 |
| `flash_rate.py` | 8.a | 1초 슬라이딩 창 최대 깜박임 Hz |
| `sound.py` | 5.c | 암소음 보정 후 SOP 측정점 최솟값 |

**구현 시 반드시 지킬 것**

- 명도 대비의 상수는 형제 프로젝트 TS `packages/core` 와 **동일해야 한다.** 갈라지면
  디자인 단계와 현장 진단이 같은 화면에 다른 값을 낸다.
- `flash_rate` 의 “깜박임 1회”는 **반대 방향 변화 한 쌍**이다. 방향 전환 하나를
  1회로 세면 2Hz 점멸이 4회/초로 나온다. 그리고 별표5는 “3회 미만”이므로
  정확히 3.0Hz 는 **부적합**이다.
- `text_height` 의 계수는 두 성분이다. `CAP_RATIO`(폰트 메트릭)는 **실측 교정 완료**,
  `OCR_BOX_FACTOR`(엔진 상자 규약)는 **미교정**이다. 후자가 `False` 인 동안
  확신도 상한 0.85 가 걸려 자동으로 검토자 큐에 들어간다. §11.3 참조.
- `sound` 의 측정점은 표준이 아니라 **본 SOP 가 정의한 값**이다. 측정 조건을
  리포트에 반드시 병기한다 — 조건 없는 dBA 값은 재현되지 않는다. §11.2 참조.
- `geometry` 의 물리 간격 0.5mm(1.b)는 촬영 오차와 겹친다. `can_confirm_pass` 가
  `False` 면 적합을 선언하지 않는다.

### L2 · 멀티모달 판단 — 모델이 해석한다

색 단독 사용 여부(4.a), 레이블 적절성(1.g·7.g), 용어 난이도(7.h),
화면 간 일관성(7.c), 지시문의 감각특성 의존, 오류 안내 정확성(7.b).

출력은 반드시 구조화한다 — `{verdict, evidence_bbox, quote, confidence}`.
자유 서술을 받아 파싱하지 않는다.

### L3 · 사람 확인 큐

L1·L2가 기준선에 못 미친 항목 + 트랙 B·C 항목이 모두 여기로 모인다.
검토자 UI는 근거 4종을 한 화면에 띄우고 승인/반려만 받는다.

## 7. 현장 수집 (`rules/capture-protocol.yaml`)

### 7.1 기준 스케일 마커 — 이 사업에서 가장 값싼 결정

신용카드 크기(85.6×54mm) 카드에 40mm ArUco 마커. 인쇄비만으로
치수 항목 6개(1.b·1.c·1.i·3.g·9.a·9.b)가 ‘추정’에서 ‘측정’으로 넘어간다.

```bash
python tools/make_marker.py --sheet     # assets/ 에 카드 4장 + A4 시트
```

- **762dpi = 정확히 30 px/mm** 로 고정한다. 이 격자에서만 카드(2568×1620px)와
  마커(1200px = 6셀 × 200px)가 정수로 떨어진다. 600dpi 로 만들면 렌더 격자가
  어긋나 검출 변이 40mm 가 아니라 **39.50mm** 로 나온다(−1.3%).
- ArUco 검출기는 마지막 검은 **픽셀 인덱스**를 코너로 돌려주므로 실제 경계보다
  1px 안쪽이다. `scale.correct_edge_bias()` 가 보정한다. 코너를 반경 방향으로
  ½px 미는 방식은 틀린다 — 정사각형에서 변이 1px 이 아니라 0.707px 만 는다.
- 호모그래피는 **한 평면에만** 성립한다. 화면 평면과 물리 버튼 평면은 깊이가
  다르므로 마커를 각 평면에 따로 둔다.
- 인쇄는 반드시 **실제 크기 100%**. 카드에 20mm 눈금자를 넣어 두었으니 인쇄 후 자로 검증한다.

### 7.2 촬영 세트

| 세트 | 내용 | 마커 | 기여 항목 |
|---|---|---|---:|
| S1 | 화면 캡처 시퀀스 (전 단계 · 확대 · 고대비 · 무보정 원본) | ● | 20 |
| S2 | 조작 영상 1회 (30fps 이상 · 음성 동시) | | 16 |
| S3 | 기기 사진 (정면·측면·하부·접사·휠체어 눈높이) | ● | 13 |
| S4 | 주변 환경 (바닥·단차·동선·눈부심) | ● | 참고 |
| S5 | 음성 녹음 (최소/최대 × 이어폰 연결/미연결) | | 11 |
| S6 | 설치 매뉴얼 PDF (선택) | | 참고 |

수집 앱의 역할은 촬영기가 아니라 **누락 방지 체크리스트**다.
필수 컷을 다 찍기 전에는 제출이 막히고, 각 컷에 `rule_id` 가 자동 태깅된다.
**입력 품질이 곧 판정 품질이므로 이 앱이 엔진보다 먼저 나와야 한다.**

### 7.3 개인정보

- 얼굴·카드번호·주민번호·성명은 **업로드 전 단말에서** 마스킹한다. 원본은 전송하지 않는다.

## 9. 실증 설계 — 정확도를 어떻게 증명할 것인가

발표자료는 “AI 정확도 90% 이상”을 약속했다. 단일 숫자로는 방어되지 않는다.

| 항목군 | 검증 방법 | 제시할 지표 |
|---|---|---|
| L1 계측형 (명도대비·문자높이·버튼치수) | 전문 실측값과 오차율 비교 | 오차 ±10% 이내 |
| L2 판단형 (색 단독·레이블·용어) | 전문가 2인 독립 판정과 일치율 | 일치율 80% 이상 |
| 트랙 라우팅 | ‘판정 불가’를 올바르게 넘겼는지 | **놓친 위반 0건 지향** |
| 처방 활용성 | 점주·운영자 인터뷰 | 개선 항목 채택률 |

정답지는 별표5 2항 사용자 검증에서 가져온다. 12명 전원 소집이 예산상 어려우면
축소 구성(전맹1·저시력1·휠체어1·고령2·비장애2 = 7명)을 쓰되 **축소 사실을 리포트에 명시**하고,
그 결과를 ‘별표5 사용자 검증 통과’로 표기하지 않는다.

**트랙 라우팅 지표가 가장 중요하다.** 실제 위반을 ‘적합’으로 넘겨버리는 것은
‘판정 불가’로 사람에게 넘기는 것보다 훨씬 나쁘다. 임계값은 이 방향으로 보수적으로 잡는다.

### 11.1 (확정) 1.c 의 144mm² 와 150mm² — 불일치가 아니다

원문 대조 결과, 두 수치는 **같은 것을 재는 서로 다른 값이 아니라 서로 다른 것을 재는 두 기준**이다.

| | 별표5 1.c | KS X 9211:2025 §5.6.2 (표면 크기) |
|---|---|---|
| 측정 대상 | 모든 작동부의 **최소경계상자(MBR)**, 기기 축에 정렬된 상태 | 버튼 및 키의 **손가락으로 누르는 부위** |
| 면적 | 144mm² 이상 | 150mm² 이상 |
| 변 | **각** 변 12mm 이상 | **한** 변 12mm 이상 |
| 근거 | 고시 — **법적 구속력** | 참고: BS EN 1332-3:2008, 5.3.1 — **권고** |
| 원본 행 | — | 38행 (§5.6.1=37, §5.6.2=38, §5.6.3=39 로 확인) |

여기서 두 가지가 따라 나온다.

**① 별표5의 144mm² 는 독립적인 제약이 아니다.**
축 정렬 경계상자는 두 변이 모두 12mm 이상이면 면적이 반드시 144mm²(=12×12) 이상이다.
실질 구속 조건은 12mm 변 하나뿐이고, 면적 조건은 확인 사살이다.

**② KS 가 더 엄격하다.**
누름 부위 면적은 경계상자 면적보다 작고, 원형·다각형이면 훨씬 작다
(KS §5.6.2 비고 3 이 “직사각형, 원형, 다각형 등 다양한 형상”을 명시).

| 버튼 형상 | 경계상자 면적 | 누름 부위 면적 | 별표5 1.c | KS §5.6.2 |
|---|---:|---:|---|---|
| 12×12mm 정사각 | 144mm² | 144mm² | 적합 | 미달 |
| 지름 12mm 원형 | 144mm² | **113mm²** | 적합 | 미달 |
| 지름 13.8mm 원형 | 190mm² | 150mm² | 적합 | 충족 |
| 13×13mm 정사각 | 169mm² | 169mm² | 적합 | 충족 |

> 지름 12mm 원형 버튼은 별표5를 통과하지만 KS 권고에는 크게 못 미친다.
> **경계상자 면적을 150 과 비교하면 이 케이스를 놓친다.**

**엔진 반영** — `calc/geometry.py` 가 두 값을 따로 계산한다.

- `Box.area` — 축 정렬 경계상자 면적 → 별표5 판정 (`MBR_AREA_MIN_MM2 = 144.0`)
- `Box.pressable_area` — 윤곽 다각형의 실제 면적(신발끈 공식) → KS 권고 (`PRESSABLE_AREA_ADVISORY_MM2 = 150.0`)
- 누름 면적을 측정하지 못했으면 경계상자로 대신 판단하지 않고 `unmeasured_pressable` 로 남긴다.

**리포트 표기** — 법적 판정과 설계 권고를 분리해 인쇄하고,
KS 수치에는 “판정이 아니라 권고”임을 명시한다.
KS 본문은 인용하지 않는다(§10).

### 11.2 (확정) 5.c 음량 — 표준 체인 어디에도 측정 거리가 없다

세 문서를 모두 추적했다.

| 문서 | 규정 내용 | 측정 거리 |
|---|---|---|
| 별표5 5.c | 65dBA 이상 조절·음소거 / 사용 후 65dBA 미만 초기화 | **없음** |
| KS X 9211 §5.3.3 b) | 스피커 음량 65 dBA 이상 조절 가능 (비고 4는 dBA 정의만) | **없음** |
| KS X 9211 §5.3.4 | 세션 종료 시 음소거 해제·65dBA 미만 자동 초기화 | **없음** |
| EN 301 549 §5.1.3.12 | "at least 65 dBA (−29 dBPaA)" | **없음** |
| EN 301 549 §5.1.3.13 | "resets the volume to 65 dBA or less after every use" | **없음** |

EN 의 **−29 dBPaA** 는 1 Pa 기준 A특성 음압이다. 65 dB SPL(re 20 µPa)을 환산하면
`20·log10(20e-6 × 10^(65/20)) = −28.98 ≈ −29 dBPaA` 로 정확히 맞는다.
즉 표준은 **얼마나 큰 소리인가는 고정했지만 어디서 재는가는 열어 두었다.**

→ 측정점은 본 SOP 가 정의한다. `rules/measurement-sop.yaml` 에 `provenance: sop` 로 표시하고,
리포트에 측정 조건을 함께 인쇄한다. 조건 없이 인쇄된 dBA 값은 재현되지 않는다.

**정의한 측정 조건**

- 기기 전면 **300mm**, 화면 중앙 정면
- 귀 높이 **1,500mm(선 자세)** / **1,150mm(휠체어 자세)** 두 지점
- **두 측정점 중 낮은 값**을 판정값으로 (보수적)
- A특성 · FAST · 3회 산술평균
- 암소음 보정: ΔL ≥ 10dB 불필요 / 3~10dB 보정 `L = 10·log10(10^(Lm/10) − 10^(Lb/10))` / < 3dB 측정 무효

**권고 수치의 출처도 확정했다** — 트리아지 시트의 18dB·12dB 는 다음에서 온다.

- 음량 조절 범위 18dB 이상 → **EN 301 549 §8.2.1.1** (Speech volume range)
- 단계식 제어의 중간 단계 +12dB → **EN 301 549 §8.2.1.2** (Incremental volume control)

둘 다 **판정이 아니라 권고**다. 리포트에 그렇게 표기한다.
구현: `engine/calc/sound.py`.

### 11.3 (교정 완료) 문자 높이 계수 — 추정이 위반을 놓치고 있었다

`tools/calibrate_text_height.py` 로 실제 폰트(맑은 고딕)를 200px 렌더해
자종별 **잉크 바운딩 박스 높이 ÷ 타이포그래픽 행 높이**를 측정했다.

| 자종 | 교정 전(추정) | 실측 평균 | 실측 최소 | 채택값 |
|---|---:|---:|---:|---:|
| 한글 | 0.86 | 0.711 | 0.708 | **0.708** |
| 라틴 대문자 | 0.72 | 0.551 | 0.539 | **0.539** |
| 라틴 혼용 | 0.62 | 0.707 | 0.577 | **0.577** |
| 숫자 | 0.74 | 0.599 | 0.554 | **0.554** |
| 한글+라틴 | 0.70 | 0.712 | 0.682 | **0.682** |

> **추정치가 전부 과대했다.** 계수가 크면 문자 높이를 크게 추정해 위반을 놓친다.
> 10mm 박스의 한글은 추정으로 8.6mm(통과)였지만 실측 계수로는 7.08mm(미달)다.
> 즉 교정 전 엔진은 **놓치는 방향**으로 틀려 있었다.

채택값이 최소인 이유 — 3.g 는 `ai_verdict_scope: fail_only` 라 AI 가 적합을 확정하지 않는다.
계수가 작으면 과소평가해 검토자에게 넘어가고(false flag, 비용은 검토 시간),
크면 과대평가해 위반을 놓친다(false pass, 비용은 과태료). 놓침이 훨씬 나쁘다.

**남은 불확실성은 분리해 관리한다.**

| 성분 | 상태 | 의미 |
|---|---|---|
| `CAP_RATIO` | **교정 완료** | 폰트 메트릭 — 이번에 실측 |
| `OCR_BOX_FACTOR` | **미교정** | OCR 엔진 상자 규약 — 엔진 확정 후 현장 표본으로 |

OCR 성분이 미교정인 동안 확신도에 상한(0.85)이 걸려 자동으로 검토자 큐로 간다.
자종별 측정 산포도 확신도를 깎는다 — 라틴 혼용은 산포 0.184 라 한글(0.008)보다 낮게 나온다.
실측 SOP 3.g 가 실측값과 AI 추정값을 함께 기록하도록 해 두었고, 그 표본이 OCR 성분 교정의 입력이 된다.

### 11.4 (확정) 지자체 제출본 — 생성기를 만들지 않는다

세 가지 길 중 **서식 채우기**를 택했다.

| 방식 | 판단 |
|---|---|
| 발주처에 물어보고 대기 | 착수가 막힌다 |
| HWP/HWPX 생성기 개발 | **채택 안 함** — 한글이 열어 주는지는 실제 한글에서만 검증된다. 파이썬 zlib 이 통과시킨 파일을 한글이 거부하는 경우가 흔하다. 검증할 수 없는 생성기를 만들고 '해결'이라 적는 것은 이 프로젝트의 원칙에 어긋난다 |
| **서식 채우기 + 표 붙여넣기** | **채택** — 지자체는 거의 언제나 자기 서식을 준다. 서식을 발명할 이유가 없다 |

구현: `engine/report/export.py`

- `to_field_map()` — 서식 채우기용 이름-값 맵 (모든 값 문자열)
- `to_hwp_edits()` — 필드 ↔ 문단 키 바인딩을 받아 `hwp_replace.py` 입력 생성
- `to_csv()` / `undetermined_csv()` — 40항목 매트릭스·미판정 표. BOM 포함으로 한글에서 안 깨진다
- `to_json()` — 전체 구조화 데이터

기본 산출은 웹 + PDF 다. 서식이 도착하면 바인딩 한 번 만들고 채우면 된다.
절차는 `export.HWP_FILL_PROCEDURE` 에 있다. **마지막 단계는 한글에서 직접 열어 확인하는 것이다.**

### 11.5 (설계로 종결) KS 이용 허락 — 허락 없이도 안전한 설계

경계를 정확히 짚으면 문제가 사라진다.

| 문서 | 성격 | 인용 |
|---|---|---|
| 고시 [별표 5] | 행정규칙 = **공공저작물** | 원문 인용 **가능** |
| KS X 9211:2025 | "상업적 활용을 금지합니다" 표시 | 본문 인용 **불가**, 조항 번호 참조는 가능 |

**법적 판정에 필요한 문언은 전부 별표5 안에 있다.** KS 는 기술적 배경이고,
우리가 필요로 하는 것은 조항 '번호'이지 '문장'이 아니다. 번호 참조는 출처 표시이지 인용이 아니다.

문제는 이 원칙이 시간이 지나면 조용히 무너진다는 것이다 —
누군가 편의상 KS 문장을 `notes` 에 붙여넣고, 그게 리포트 템플릿으로 새어 나간다.
그래서 사람의 주의가 아니라 **CI 가 막는다**.

```bash
python tools/check_ks_copyright.py                 # 저장소 검사
python tools/check_ks_copyright.py --report r.md   # 생성된 리포트도 검사
```

검사 항목: ① `ks_ref` 가 조항 번호 형식만 담는지(종결어미가 보이면 본문을 옮긴 것)
② 저장소에 KS 본문 특유 문구가 있는지 ③ 생성 리포트에 새어 나갔는지.
가드 자체도 테스트한다 — 위반을 심어 잡히는지 확인하는 케이스가 있다.
항상 통과하는 가드는 가드가 아니기 때문이다.

**남은 행정 절차** — 한국표준협회 e-standard 표준 이용 문의.
KS 조항 해설을 대외 자료에 싣고 싶어질 때 필요하다. **착수를 막지 않는다.**

### 11.6 (확정) 1.f — B_OWNER 유지, 선택적 AI 스크리닝 추가

실물 매체를 일부러 잘못 넣는 행위는 **매체 걸림·리더 손상 위험**이 있다.
조사원이 임의로 수행할 수 없고 점주 동의와 입회가 필요하다.
따라서 기본 판정 주체는 점주다.

다만 점주가 동의해 **S2-05(오투입 재현)** 컷을 촬영한 경우에는 AI 가 1차 스크리닝한다.

```yaml
optional_ai_screen:
  shot: S2-05
  ai_role: screen
  ai_verdict_scope: fail_only    # 위반은 잡되 적합은 확정하지 못한다
```

이때도 최종 확정은 점주 응답이 한다 —
영상 한 컷으로는 '모든 매체·모든 방향'을 확인할 수 없기 때문이다.
